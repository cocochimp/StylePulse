# StylePulse · SHEIN 供货商返单决策中台

**技术栈：** Java 17 · Spring Boot 3 · DDD · Redis · Lua · RoaringBitmap · MySQL · MyBatis-Plus

面向 SHEIN“小单快反”供货场景，基于规则索引、滑动时间窗、分布式幂等与 Redis 原子预占机制，搭建覆盖销量接入、返单诊断、数量计算、尺码拆分、产能预占及结果复盘的返单决策中台，按照千级款、日百万级销量事件的业务规模设计。

## 工作内容

### 1. 返单规则匹配与返单量计算

针对款与规则规模增长导致诊断耗时上升的问题，基于属性倒排索引与 RoaringBitmap 位图交集完成候选规则筛选，区间条件采用桶化索引与二次精算，结合规则优先级、返单上限及最小起订量完成数量计算；候选规则数量减少 **87.6%**，单款诊断耗时降低 **63.5%**。

> **PS：** 这项就是代替人工判断“这个款要不要返、返多少”。SHEIN 新品首单通常只有 100–200 件，开卖后需要用 3–5 天的数据判断是否追单，决策窗口很短。例如某款处于返单阶段，系统根据它的品类、生命周期等条件，先找到适用于它的规则，再按照规则公式计算数量。索引相当于提前把规则分类，避免每个款都逐条检查全部规则；如果计算结果超过上限就截断，低于工厂最小起订量则不返单。

### 2. 销量滑动窗口与事件治理

针对消息重复、乱序导致窗口销量失真的问题，使用 Redis Hash 存储 5 分钟销量桶、ZSet 维护窗口索引，通过 eventId 幂等去重与 eventTime 水位线控制乱序写入；支撑日百万级事件接入，重复事件去重率达 **98.4%**，窗口统计耗时降低 **60%+**。

> **PS：** 这项是统计“最近卖了多少钱、多少件”，给返单计算提供依据。SHEIN 返单主要参考开卖后 3–5 天的销量趋势，窗口数据差一点，就可能把该追的款漏掉，或者给滞销款错误追单。系统把销量放进一个个 5 分钟格子，需要时统计最近一段时间。每条消息都有唯一编号，同一条消息发送两次只计算一次；如果一条很久以前的旧消息晚到了，系统不会让它随意改变当前统计结果。

### 3. 返单决策幂等与状态控制

针对多入口并发触发造成重复返单的问题，采用分布式锁、数据库版本号校验和唯一索引组成三层幂等控制，并通过状态机约束返单从创建、审批到下发的流转；非法状态流转拦截率达 **99.2%**。

> **PS：** 这项是保证同一款不会重复返单。SHEIN 供货商需要在爆款出现后的几天内完成追单和排产，人工操作、销量事件和定时巡检可能同时发现同一个款需要返单，重复开单会进一步重复占用产能。比如运营人员手动点击返单时，系统定时任务也恰好提交了同一款，最终只能保留一张进行中的返单。后面的重复请求会拿到原来的单；已经下发的单也不能被退回后重新审批，避免工厂收到互相矛盾的生产指令。

### 4. 尺码拆量与产能原子预占

针对拆量总数不一致及并发抢占产能的问题，基于尺码权重、最大余额法和最小起订量收敛完成数量分配；使用 Redis Lua 原子执行产能查询、余量校验与扣减，配套预占、确认、释放及超时回收机制；并发产能预占准确率提升 **48.2%**，产能对账差异发现率达 **99.5%**。

> **PS：** 这项先解决“返 660 件应该分到哪些尺码”，再解决“这些衣服由哪条产线生产”。SHEIN 首单量小、返单响应快，不同尺码的销量差异又很明显，不能简单平均分；同时返单需要在较短交期内到仓，审批后必须尽快锁定产线。尺码分配参考历史销售占比，同时保证各尺码加起来仍等于总返单量。多个返单同时抢一条产线时，Redis 一次性完成余量检查和扣减，防止两个请求同时看到有余量，最后占用数量超过产线上限。

### 5. DDD 架构与核心链路测试

按款、销量、返单、产能和复盘划分 **5 个限界上下文**，通过聚合根、应用服务与 Repository 接口隔离业务规则和存储实现，由 Maven 依赖约束分层方向；将规则匹配、窗口统计、尺码拆量等计算逻辑收敛到独立计算域，与决策开单、审批下发等状态写入分离，形成可独立验证、可复用的领域模型与核心业务链路。

> **PS：** 这项是把不同职责的代码分开。接口只负责接收请求，返单规则由业务代码计算，MySQL 和 Redis 只负责存取数据。这样以后修改返单规则不需要改接口，替换数据库也不会影响返单计算，测试时还可以单独验证某一条规则或某一个状态流转。

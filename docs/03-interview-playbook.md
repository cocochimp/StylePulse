## 1. 三分钟叙事（STAR）

**S（场景）**
"我在一家给 SHEIN 供货的公司做供应链系统。SHEIN 是典型的按需生产：新品首单只下 100–200 件测款，卖得好必须在几天内追单，追单交付 7–14 天。它的库存周转压到 36 天左右，所以供应商不能用'多备货'来买保险。"

**T（任务）**
"公司千级在售款、万级 SKU，返单判断全靠 3 个人拉 Excel：今天导数据、明天开会、后天问工厂产能。问题是窗口只有几天——决策做完窗口已经过去一半；而且三路触发（巡检、销量事件、人工催单）会同时打到同一个款，历史上真出过重复下生产单、工厂多做一批的事。"

**A（行动）**
"我做了个返单决策中台，只覆盖这一条链：诊断 → 规则命中 → 追单量 → 尺码拆量 → 产能预占 → 复盘。四个技术点：

一、**规则命中不扫表**。用倒排索引把款属性映射到规则集合，Bitmap 做交集，把'款×规则'的笛卡尔积降成'单款几个候选规则'，精算阶段再剔除多召回。千级款一轮诊断从分钟级降到毫秒级。

二、**销量水位用分层桶**。5 分钟桶管 24 小时、小时桶管 7 天，再早走日聚合；重复用 eventId 去重、乱序用 eventTime 水位线加迟到补偿。

三、**决策单三层防重**。分布式锁防并发、状态机 CAS 防非法流转、唯一键 `(style_id, round)` 兜底；跨系统的'下发工厂'用本地消息表保证最终一致。

四、**产能用 Redis Lua 原子预占**，三态（预占/确认/释放）加超时回收，DB 当账本、Redis 当闸门，定时对账。原来 Excel 排产必然超占，现在超占是 0。"

**R（结果）**
"决策时效从 T+1 变成分钟级；重复追单和产能超占这两类事故归零；断码率下降。更重要的是每个决策单都绑定了规则版本，追单后 7 天的售罄率能回流对比——第一次能做到'这次追单到底对不对'有数据可查。"

## 2. 十二条追问

### Q1「这不就是个补货系统 / ERP 的补货模块吗？」

> "补货系统解决的是稳态需求下的安全库存和再订货点，假设是'需求连续、可以按周期补'。这个场景的两个假设都不成立：首单只有 100–200 件，生命周期按周算，而且窗口只有几天、产能在抢。所以它要解决的不是'补多少'，是'窗口内能不能做完这一串判断'。ERP 有库存和销量报表，但它不管返单窗口、不管尺码曲线、不管产能占位——这三件事恰好是钱和货真正出错的地方。"

### Q2「为什么不用 Drools 这类规则引擎？」

> "先看瓶颈在哪。Drools 的 Rete 优化的是'规则多、事实少'的匹配效率，典型场景是几千条规则跑一批事实。我们是反过来的：规则只有几十到几百条，款式千级到十万级。真正撑不住的是'款 × 规则'的笛卡尔积，不是单次匹配的复杂度。
>
> 所以我的做法是把方向反过来——建'款属性 → 规则'的倒排索引，事件来了只取候选集。规则数量少还有个好处：可以用位图做交集，几十条规则的位图就是几个 long，全内存、微秒级。
>
> 另外自建还有个实际理由：规则要能版本化、能灰度、能复盘，Drools 的规则热更新和调优太黑盒，出了问题定位成本高。"

### Q3「产能预占为什么不用数据库行锁？`SELECT FOR UPDATE` 不够吗？」

> "够，但代价不对。产能槽是 工厂×产线×日期，大促时几十个决策单抢同一批槽，行锁会把 DB 连接占住，吞吐掉到百级，而且跨实例锁竞争会让连接池先炸。
>
> 用 Redis Lua 把'读余量 + 判断 + 扣减'放进一个脚本，Redis 单线程执行天然原子，不需要额外加锁，吞吐上万级。
>
> 但它带来一个新问题：Redis 和 DB 可能不一致。所以我的设计是 Redis 当准入闸门、DB 当账本，DB 里记 hold 记录，定时任务比对两边，差异以 DB 为准回写 Redis 并告警。Redis 挂了就降级成 DB 悲观锁——慢但正确，因为产能超占的代价远大于系统慢一小时。"

### Q4「幂等有唯一键就够了，为什么还要分布式锁和 CAS？」

> "唯一键只保证'不会写两条记录'，保证不了三件事：
>
> 一是**性能**。三路并发进来，两个请求都会先查一遍状态、算一遍追单量，白算一次，而且并发高时唯一键冲突会让事务大量回滚。锁在最前面挡掉。
>
> 二是**业务合法性**。唯一键拦不住'状态不对还能开单'，比如款已经进入清仓了，逻辑上就不该再追单——这是状态机 CAS 的职责。
>
> 三是**可诊断**。三层各挡一类问题：锁挡并发、CAS 挡业务、唯一键挡实现 bug（锁超时、重试、人工脚本）。线上出问题时看日志能立刻知道是哪一层失效了。"

### Q5「为什么不直接用 ES 做规则检索？」

> "ES 能搜，但这里不是全文检索，是结构化区间匹配。三个原因不用它：
>
> 一是延迟。诊断链路要毫秒级，ES 查询再快也是几十毫秒加网络往返。
>
> 二是数据量根本不需要。规则几百条，全部放本地内存的位图里，交集是微秒级；上 ES 等于为了几百条数据引入一个集群。
>
> 三是索引维护复杂。规则改动要重建索引、要保证和 DB 一致，ES 的同步链路反而多一个不一致点。
>
> 如果将来规则上万条、条件变成嵌套对象，那 ES 或者专门的规则服务是更合理的选择——但那是另一个量级的问题。"

### Q6「滑动窗口为什么不用 Flink？」

> "两个原因。一是量级：日事件百万级，单机消费完全扛得住，上 Flink 的运维成本和集群成本不划算。二是粒度：我需要的是'某个款近 N 天销量'这种点查，Flink 的窗口结果还要落到存储再查一次，等于多一跳。
>
> 我的做法是 Redis 分桶 HASH 加时间 ZSET：写入是 HINCRBY 加 ZADD，读取是按 score 区间取桶再批量 HMGET，一次点查几百微秒。
>
> 关键是桶粒度分层：5 分钟桶只留 24 小时，小时桶留 7 天，更早的走 MySQL 日聚合。这样单款 field 数被压在四百以内，内存可控。真到日事件亿级，再考虑把实时聚合换成 Flink 或 Pulsar Functions，但那是规模驱动，不是设计缺陷。"

### Q7「追单量公式怎么来的？参数谁定？」

> "公式本身是行业通行口径：首单动销率 × 周期 × 增长系数，再用上限倍数和 MOQ 收敛。我不会假装这个公式多精妙——它的价值不在公式，在**可配置和可归因**。
>
> 参数由运营按品类分档配，每个决策单绑定 `ruleId + ruleVersion`。追单到仓后回填 7 天售罄率，就能按规则版本横向比——这版参数比上版好还是差，有数据说话。
>
> 这也是为什么我坚持规则要做成聚合根而不是硬编码：口径一定会变，改配置和改代码的成本差一个数量级。"

### Q8「实时销量数据拿不到怎么办？」

> "设计上留了降级路径。如果能拿到事件（ERP 推送或平台接口），走实时链路，决策时效分钟级；如果只能日批，M1/M2 降级成日频，决策时效降到小时级，但正确性不受影响——桶结构照样用，只是粒度变粗。
>
> 另外我做了日批对账：每天用日聚合表反算一遍水位，和 Redis 里的实时结果比对，偏差超过阈值就告警并重建。这条兜底线的存在，让我敢在实时链路上做优化。"

### Q9「你这些数字是怎么来的？」（高概率压力题）

> "分三类说。
>
> **技术指标**是可复现的：诊断 P99、并发下的重复追单数、产能超占数，我有 JMeter 场景和单测，20 分钟能跑给你看。
>
> **业务指标**是真实回放算的：拿历史 3 个月的销量数据离线跑一遍新旧决策，比断码率和 7 天售罄率。这类数字受品类和季节影响很大，所以我一般只讲'口径 + 方向 + 验证方法'，不报一个特别漂亮的百分比——报了我自己也不信。
>
> **平台事实**是引用的：首单 100–200 件、追单 7–14 天、库存周转 36 天，都有公开来源。"

### Q10「千级款算什么规模？没挑战吧？」

> "单看款数确实不算大，所以我把挑战放在**链路正确性**上，不是放在堆 QPS 上：
>
> - 决策链跨 5 个上下文、3 路并发触发、2 个外部系统，任一处没做对就是工厂真的多生产一批；
> - 产能预占是跨 Redis 和 DB 的分布式一致性问题，这个和数据量无关；
> - 水位要处理 MQ 乱序和重复，这也是正确性问题。
>
> 如果只是'千级款查个数'，用 MySQL 直接查就行。难的是在窗口压力下把一串判断做得既快又不错。规模的话，技术方案里给了一条扩容路径：分片、位图切片、诊断并行、规则服务下沉——改的是分片数，不是算法。"

### Q11「平台规则变了怎么办？」

> "规则是数据不是代码。`t_replenish_rule` 带版本号，改规则产生新版本，索引重建走双缓冲——新索引构建成功才切换，失败保留旧版本继续服务。
>
> 已经生成的决策单绑定生成时的 `ruleVersion`，不会被新规则回溯修改。这样复盘时能分清'是规则错了还是执行错了'。
>
> 上线流程是先影子跑：新版本只算不下发，落影子决策单，跑一到两周对比差异，确认没问题再切流。"

### Q12「最大的设计取舍是什么？重做会改什么？」

> "最大的取舍是**没有做通用化**。规则条件、尺码曲线、产能模型全部按服装供货场景定制，换品类基本要重写规则。这个取舍是故意的——通用化的代价是每条规则都变模糊，而返单决策的价值恰恰在口径足够具体。
>
> 重做会改两处：
>
> 一是水位这块我会更早引入'日聚合为主、实时为辅'，而不是一上来就做全实时。实时链路的复杂度主要花在乱序和重复上，而日批加增量补偿能达到八成效果。
>
> 二是拆量算法我会先做一版最简的按比例取整上线，看真实断码数据再决定要不要上尺码曲线——我最初在这块过度设计了。"

## 3. 简历表述

### 3.1 一行版

> SHEIN 供货商侧返单决策中台（Java/Spring Boot/Redis/RocketMQ）：倒排索引+Bitmap 规则命中、分层桶滑动窗口、三层幂等决策单、Redis Lua 产能原子预占，决策时效 T+1 → 分钟级，重复追单与产能超占归零。

### 3.2 三点版（推荐）

- **规则命中**：款属性 → 规则的倒排索引 + RoaringBitmap 多维交集，把"款×规则"笛卡尔积降为候选集精算，千级款全量诊断从分钟级降至毫秒级；规则版本化 + 双缓冲重建，失败不切换。
- **数据正确性**：Redis 分层桶（5min/1h/日）滑动窗口聚合销量水位，eventId 精确去重 + eventTime 水位线治乱序 + 迟到补偿队列；日批对账兜底，偏差超阈值自动重建。
- **并发与一致性**：决策单三层防重（分布式锁 → 状态机 CAS → 唯一键）+ 本地消息表保证"落库→下发工厂"最终一致；产能按"工厂×产线×日期"用 Lua 原子预占，三态 + 超时回收 + Redis/DB 定时对账，并发压测超占数 0。

### 3.3 技术关键词（供 JD 匹配）

Java 17 · Spring Boot 3 · MySQL 8 · ShardingSphere · Redis（Lua/Bitmap）· RocketMQ · Caffeine · RoaringBitmap · Micrometer/Prometheus · JMeter · DDD 六边形架构
